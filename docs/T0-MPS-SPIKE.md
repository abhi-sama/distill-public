# T0: MPS training spike (go/no-go)

**Verdict: GO.** Laya fine-tunes on an Apple M5 Pro Mac (64 GB) on the Apple GPU (MPS).
- No op fell back to the CPU or errored.
- Loss goes down.
- The saved checkpoint loads and predicts through `laya.load()`.
- A real run fits in memory with room to spare and finishes in minutes to about 2 hours.

Script: [`scripts/spike_train.py`](../scripts/spike_train.py). Raw evidence (one `metrics.json` per run, plus `/usr/bin/time -l`): [`docs/t0-mps-spike/`](t0-mps-spike/).

## The five questions

| Question | Answer |
|---|---|
| Does it run on MPS? Which ops fall back to CPU or error? | **Yes. None fall back and none error.** All 16 MPS runs ran with `PYTORCH_ENABLE_MPS_FALLBACK` unset. In that mode PyTorch raises for any op with no MPS kernel rather than falling back, so a missing op would have crashed the run. The script also records any fallback warning or `NotImplementedError` op name in `metrics.json`. Every run recorded `[]`, and the raw stderr logs have no MPS warning. The only CPU work is by design, as in the notebook: tokenising and collating batches, the 3-scalar L-BFGS temperature fit, and writing the checkpoint. |
| Peak memory | **10.2-11.8 GB** with gradient checkpointing (the notebook's setting). **16.8-22.3 GB** without it. The worst case is fp32, no checkpointing, all sequences at 512 tokens. Measured as the process's peak physical footprint (`/usr/bin/time -l`), which includes Metal buffers. Metal's recommended working-set limit on this Mac is 51.8 GB. |
| Seconds per step | One step = one optimizer update = 32 sequences (micro-batch 8 x grad-accum 4). **Short synthetic items (~100 tokens):** 2.9-3.0 s (fp32 + checkpointing), 1.7-2.1 s (bf16, no checkpointing). **512-token items:** 12.8 s and 6.5 s. The Mac was shared during the spike, so repeats varied by about 20%; the 512-token figures are the slower of two repeats. Projections are in the "Projected real run" section below. |
| Does the loss go down? | **Yes.** In the 200-item, 1-epoch run, held-out soft cross-entropy fell from 1.399 to 0.811 and held-out accuracy rose from 0.45 to 0.75. In the 800-item, 4-epoch run, the per-epoch mean training CE fell every epoch (0.771, 0.602, 0.581, 0.573), and held-out CE fell from 1.035 to 0.598 (accuracy 0.65 to 0.91). |
| Does the checkpoint load and predict through laya's loader? | **Yes.** `laya.load(checkpoint, device="mps")` loads it in under 1 s. `predict_batch` returns all four typed answers. On fresh rows, laya's accuracy rose from 0.64 (base) to 0.875 (fine-tuned) after 200 items and 1 epoch, and from 0.60 to 0.95 after 800 items and 4 epochs. Laya's probabilities match the in-memory model: max gap 0.0015 on the 4-epoch run, argmax agreement 100%. The one exception is the fp16 run; see finding 3. |

MPS did not fail, so the planned CPU fallback was not needed. A 40-item CPU run was still done to check the `--device cpu` path. It works, at 235-250 padded tokens/s against 1,449 for the same config on MPS (about 6x slower).

## Setup

- **Machine:** Apple M5 Pro, 64 GB, macOS 26.6.2.
- **Software:** a laya venv: Python 3.14.7, torch 2.14.0, transformers 5.17.0, laya 0.3.17.
- **Base model:** `convaiinnovations/laya` root checkpoint, revision `55cf4c4` from the local HF cache. That is a ModernBERT-large encoder plus a 2-layer typed-decision head, 421.3M parameters, with max_len 512 and head_max_len 192.
- **Training loop:** a single-process port of `train_ddp.py` from laya's Kaggle notebook (`laya_finetune_typed_decisions_2xT4_kaggle.ipynb`):
  - RLCD policy gradient on proper-scoring-rule rewards (4 noise samples, sigma annealed from 0.4 to 0.1), plus soft cross-entropy at weight 1.0;
  - AdamW with encoder lr 2.5e-5, head lr 1e-4, weight decay 0.01, cosine schedule, gradient clipping at 1.0;
  - a 10% calibration slice (at most 400 items) held out before training, then one temperature fitted per question type with L-BFGS;
  - checkpoint written in laya's layout.
- **Data:** generated by `generate_rows()` in the script: templated support tickets for a support-ticket escalation decision. Each ticket asks four questions, in the notebook's `{state, questions, gold}` row format:
  - `escalate` (noul);
  - `urgency` (score, 4 levels);
  - `category` (choice, 5 options);
  - `manipulation` (noul).

  Gold labels are soft, teacher-style probabilities: 20% borderline, 20% with prompt-injection text, 15% long. The generator is deterministic for a given seed.
- **What "200 items" means:** 200 (state, question) training items, the unit the notebook calls items. With 4 questions per ticket, that is 50 tickets. The other reading, 200 tickets, is covered by the 800-item run.

## Results: 200 items, 1 epoch, MPS

Six optimizer updates per run. Held-out = the 20-item calibration slice. "laya acc" = accuracy through `laya.load()` on 64 decisions from 16 fresh tickets, shown as base → fine-tuned. "gc" = gradient checkpointing.

| Config | s / step | seq / s | Peak memory | Held-out soft CE | Held-out acc | laya acc | Reload gap |
|---|---|---|---|---|---|---|---|
| fp32 + gc (the notebook recipe, fp32 instead of fp16) | 2.94 | 9.7 | 11.6 GB | 1.399 → 0.811 | 0.45 → 0.75 | 0.64 → 0.875 | 0.012 |
| fp32 | 2.47 | 11.7 | 18.7 GB | 1.399 → 0.781 | 0.45 → 0.85 | 0.64 → 0.89 | 0.010 |
| bf16 + gc | 1.97 | 14.5 | 11.8 GB | 1.393 → 0.799 | 0.45 → 0.75 | 0.64 → 0.89 | 0.010 |
| **bf16** | **1.67** | **17.7** | 16.8 GB | 1.393 → 0.792 | 0.45 → 0.80 | 0.64 → 0.81 | 0.010 |
| fp16 + gc (the notebook's CUDA precision) | 1.96 | 14.1 | 10.8 GB | 1.399 → 1.208 | 0.45 → 0.50 | 0.64 → 0.625 | **0.129** (finding 3) |

**Sustained run in the recommended config** (bf16, no gc, 800 items, 4 epochs; `mps-bf16-800x4.json`):
- **Training time:** 360 micro-batches and 92 updates in 192.6 s. Throughput was flat across epochs at 14.4, 15.7, 15.1 and 14.9 seq/s, so the GPU did not throttle over about 3.5 minutes.
- **Peak memory:** 20.6 GB.
- **Temperatures:** fitted for all three types, [1.05, 1.06, 1.30] for choice, score and noul.
- **Reload gap:** 0.0015.

## 512-token benchmark (upper bound for long inputs)

Every state is padded to fill `max_len` = 512 tokens. Each run times 4 optimizer updates, and the first update is excluded as warm-up. Two runs per config:

| Config | seq / s | Padded tokens / s | Peak memory |
|---|---|---|---|
| fp32 + gc (notebook recipe) | 2.48 / 2.73 | 1,270 / 1,398 | 10.3 GB |
| fp32 | 3.36 / 3.55 | 1,720 / 1,818 | 22.3 GB |
| bf16 + gc | 3.97 / 4.29 | 2,033 / 2,196 | 10.3 GB |
| **bf16** | **4.89 / 5.76** | **2,504 / 2,949** | 19.2 GB |

Padded tokens per second hold roughly steady from short to long batches: about 2,500-2,950 for bf16 without gc, and about 1,270-1,450 for the notebook recipe. The formula below uses that.

## Projected real run (4 epochs)

Training seconds ≈ 4 × N_train × mean padded length / R.
- N_train is the item count minus the calibration slice.
- R ≈ 2,500 padded tokens/s for bf16 without gc, or ≈ 1,270 for the notebook recipe.

The table uses the slowest measured rates:

| Items (N_train) | bf16, short items (~100 tokens, 15.0 seq/s) | bf16, every item 512 tokens (4.89 seq/s) | Notebook recipe, every item 512 tokens (2.48 seq/s) |
|---|---|---|---|
| 3,000 (2,700) | 12 min | 37 min | 73 min |
| 6,000 (5,600), the notebook's reference size | 25 min | 76 min | 2 h 31 min |
| 10,000 (9,600), the product design's target | 43 min | 2 h 11 min | 4 h 18 min |

Loading, evaluation, calibration, saving and the reload check add under a minute. Real tickets are likely 100-300 tokens, so the realistic range for bf16 is about 25-90 minutes for 6k-10k items. The notebook reports about 4-6 minutes for 6k items on 2x T4 (its own claim, not measured here). The Mac is roughly 4-19x slower, but the 10k-item worst case in bf16 still fits the product design's "English to model ≤ 3 h" budget.

## Findings for T5 (`distill train`)

1. **Use bf16 autocast on MPS, with no GradScaler.** It is the fastest config that learns: about 2x the notebook recipe's throughput at 512 tokens. The base checkpoint's own config also says `amp_dtype: bf16`.
2. **Turn gradient checkpointing off on 64 GB Macs.** That gives 21-35% more throughput for a peak of 17-22 GB instead of 10-12 GB. Keep it as a flag for smaller machines.
3. **fp16 + GradScaler, the notebook's CUDA recipe, loses the first updates, and a tiny fine-tune can then vanish at inference.**
   - GradScaler starts at scale 65,536 and skipped updates 1-3 of the 6 in the 200-item run (scale fell to 8,192), while the cosine schedule kept advancing. So only three low-learning-rate updates landed.
   - Those updates are about 1e-5 per weight, below fp16's resolution. Laya runs fp16 autocast on MPS, which rounds them away. Its predictions then differ from the live fp32 model by up to 0.13, even from an fp32-saved checkpoint (`mps-fp16-gc-save32.json`: gap 0.1297, argmax agreement 96.9%). In that run the weights and the live evaluation are both fp32, so laya's fp16 autocast is the only difference left. Running laya on that checkpoint in fp32 on both MPS and CPU agrees to 0.0001.
   - On the real-shaped 4-epoch run the gap is 0.0015. So this only bites very short runs, but **T5 should keep the reload comparison (`max_abs_prob_diff_vs_live_model`) as a gate after every training run.**
4. **Save fp32 weights.** The notebook saves fp16. On CPU, where laya runs in fp32, fp16 storage changed a 2-update fine-tune's predictions by up to 0.105, against 0.000 with fp32 storage (`cpu-fp32-gc-40*.json`). fp32 costs 1.7 GB instead of 0.84 GB, and `laya.load()` accepts both. The script has `--save-dtype`.
5. **Notebook details the port changed or flags:**
   - The notebook counts cosine `T_max` as `n // (micro × accum) × epochs`. That misses the final partial accumulation group, so the learning rate runs past its minimum and rises again at the end. The port counts real optimizer steps.
   - The notebook builds items at max_len 512 / head_max_len 192 but writes 1024 / 256 into the saved config. The port keeps the base values in both places.
   - The notebook clamps fitted temperatures to [0.1, 10], but laya only applies [0.5, 5], with a load-time warning (seen in the fp16 run: 5.2 → 5.0). T5 should clamp to laya's range when fitting.
   - `fit_one_temp` keeps 1.0 for any question type with fewer than 10 calibration items. With a 10% slice and one score question per ticket, this decision needs at least about 400 items before all three types are fitted. The 200-item runs fitted only the noul temperature.
6. **Warm-up:** the first micro-batch takes about twice as long as later ones (0.7-1.5 s against 0.3-0.7 s on short items), because of kernel compilation and allocator warm-up. Timing figures leave out the first update. It doesn't matter for real runs.
7. **Upstream warning, harmless here:** the base checkpoint ships a `choice:11+` temperature of 0.1006, which laya clamps to 0.5 with a warning whenever the base model is loaded. Our fitted config drops `temperature_by_options`, as the notebook does.

## Limits of this spike

- **Synthetic data only.** Templated tickets, because the spike tests training mechanics, not data quality. All accuracy numbers come from the same template family, so they show that learning happens, not that it generalises. The held-out sets are small: 20 and 80 items.
- **No run longer than about 3.5 minutes.** Throughput was flat over the 4-epoch run, but a 1-2 hour run might throttle thermally. That is not measured.
- **Shared machine.** A VM and other processes ran during the spike (load average 3.5-4.5). Hence the ~20% run-to-run variance and the use of the slowest numbers.
- **Not tried:** the multilingual checkpoint (256k-token vocabulary, so more memory), `torch.compile`, length-bucketed batches. Short batches here were 177 tokens padded against 101 real, so bucketing could cut up to about 40% of the time.

## Reproduce

```bash
PY=python   # a Python with torch, transformers and laya installed
# headline run: notebook recipe, 200 items, 1 epoch
$PY scripts/spike_train.py --device mps --precision fp32 --out /tmp/t0/mps-fp32-gc
# recommended config, real-shaped schedule
$PY scripts/spike_train.py --device mps --precision bf16 --no-grad-ckpt --n-items 800 --epochs 4 --check-rows 32 --out /tmp/t0/mps-bf16-800x4
# 512-token throughput benchmark
$PY scripts/spike_train.py --device mps --precision bf16 --no-grad-ckpt --bench-seq-len 512 --bench-updates 4 --out /tmp/t0/bench
# CPU path
$PY scripts/spike_train.py --device cpu --precision fp32 --n-items 40 --check-rows 4 --out /tmp/t0/cpu
```

Every run writes `metrics.json` (per-micro-batch history, timing, memory, eval before and after, temperatures, reload check, fallback ops and warnings), `data.jsonl` (the generated rows) and `checkpoint/`. Each evidence file also records its exact command line. A rerun of the headline command with the final script matched the committed evidence: optimizer steps landed on the same micro-batches with the same learning rates, and eval numbers agreed to 3-4 decimals (MPS kernels are not bit-deterministic).

Tests: `python -m pytest tests/test_spike_train.py` (needs torch, transformers, laya and pytest; 18 tests, about 3 s). They cover:
- the data generator (deterministic, and valid under laya's `_check_question`);
- target ordering;
- the calibration split;
- the RLCD + CE loss (its CE term, masking, and that it decreases under optimisation);
- temperature recovery;
- device refusal and fallback-op capture;
- bench mode;
- an end-to-end run of `main()` on a tiny random ModernBERT checkpoint, on CPU and MPS, reloaded through `laya.load()`.

The tests need no model download. torch, transformers and laya are not project dependencies yet, so CI skips this test module.

## VERDICT: GO

- **Runs on MPS:** 16 of 16 runs completed with CPU fallback disabled. Zero ops fell back and zero errored.
- **Peak memory:** at most 22.3 GB of 64 GB (Metal limit 51.8 GB). 10-12 GB with gradient checkpointing.
- **Speed:** 1.7-3.0 s per 32-sequence step on short items, 6.5-12.8 s at 512 tokens. A 4-epoch run on 3k-10k items takes about 12 min to 2 h 11 min in bf16, depending on input length.
- **Loss goes down:** held-out CE 1.399 → 0.811 after 1 epoch; 1.035 → 0.598 after 4 epochs, falling every epoch.
- **Checkpoint:** loads through `laya.load()` and predicts. Laya accuracy went from 0.60 to 0.95, with a 0.0015 probability gap to the live model.
- **Recommendation for T5:** `--device mps`, bf16 autocast, gradient checkpointing off, fp32 checkpoint weights, and the reload check kept as a gate.
